# For contributors

**Audience:** you want to add a test, fix a bug, expand coverage, or write an adapter. This document is a *task index* — for each thing you might want to do, it points at the right place in the canonical reference material rather than duplicating it here.

## Repository orientation

Start with the project README for an overview of the data model, directory structure, and how the pieces fit together:

- [README: Data model](https://github.com/CalConnect/iso-8601-test-suite/blob/main/README.adoc#data-model) — ModSpec terminology, CURIE-style identifiers, clause references.
- [README: Directory structure](https://github.com/CalConnect/iso-8601-test-suite/blob/main/README.adoc#directory-structure) — what lives in `requirements/`, `tests/`, `profiles/`, `results/`, `adapters/`, `lib/`, `schema/`, `site/`.
- [CLAUDE.md](https://github.com/CalConnect/iso-8601-test-suite/blob/main/CLAUDE.md) — operational conventions for working in the repo: autoload discipline, validation, ID naming.

The rest of this document maps common tasks to their canonical instructions.

## Task index

| Task | Where to look
|---|---
| Add a requirement | Read an existing class in `requirements/8601-{1,2}/*.yaml`, copy its requirement shape (the `id`, `clause`, `statement`, optional `format` and `pattern` fields), and append. Run `ruby scripts/validate`.
| Add a conformance test | Read an existing class in `tests/8601-{1,2}/*.yaml`. Each test has `id`, `description`, `test_type`, `requirements`, `given`, and `expect`. Test type must be one of: `parsing`, `generation`, `validity`, `equivalence`, `arithmetic`, `round_trip`. See [test types](/docs/test-types).
| Add a profile | [README: Creating a new profile](https://github.com/CalConnect/iso-8601-test-suite/blob/main/README.adoc#creating-a-new-profile). Worked examples: `profiles/rfc-3339.yaml` (tightest), `profiles/w3c-datetime.yaml`. See also [For profile authors](/docs/profile-authors) for the narrative.
| Add an adapter (Ruby) | [README: Writing a new adapter](https://github.com/CalConnect/iso-8601-test-suite/blob/main/README.adoc#writing-a-new-adapter). Template: `adapters/TEMPLATE.rb`. Register in `lib/test_suite/capability_matrix.rb`'s `ADAPTER_DEFS`.
| Add an adapter (other language) | [README: Exec adapter](https://github.com/CalConnect/iso-8601-test-suite/blob/main/README.adoc#testing-non-ruby-implementations-exec-adapter). Speaks newline-delimited JSON over stdin/stdout. Working examples: `adapters/python-datetime.py`, `adapters/node-datetime.js`, `adapters/rust-chrono/`, `adapters/c-stdio.c`, `adapters/cpp-chrono.cpp`, `adapters/JavaDateTime.java`.
| Add a conformance result | [README: Recording conformance results](https://github.com/CalConnect/iso-8601-test-suite/blob/main/README.adoc#recording-conformance-results). Template: `results/TEMPLATE.yaml`. Schema: `schema/conformance-result.yaml`. Set `declared_conformance_classes` honestly.
| Fix a bug in a script | Scripts live in `scripts/`. They use `require_relative '../lib/test_suite'` as the single entry point. All modules are autoloaded; do not introduce `require_relative` inside `lib/`. See [CLAUDE.md](https://github.com/CalConnect/iso-8601-test-suite/blob/main/CLAUDE.md) for conventions.
| Fix a bug in the dashboard | `site/` is a Vite + Vue 3 app. Run `cd site && npm run dev` for hot reload. Build with `cd site && npm run build`. Data is regenerated by `ruby scripts/capability-matrix`.
| Improve validation | [README: Validating the test suite](https://github.com/CalConnect/iso-8601-test-suite/blob/main/README.adoc#validating-the-test-suite). Phases are registered in `lib/test_suite/suite_validations.rb`'s `build_phases` array — append, don't fork.
| Add a new test type handler | `lib/test_suite/test_type_handlers.rb` — register a handler in the `HANDLERS` hash. The handler decides how to dispatch the test to an adapter.
| Report a bug | Open an issue at the [project repository](https://github.com/CalConnect/iso-8601-test-suite). Include the test ID (`conf-test:...`), the requirement ID (`req:...`), and observed-vs-expected behavior.

## Conventions

These are project-wide; some are enforced by `ruby scripts/validate`, others by review.

### Identifiers

- Format: `prefix:local-name` (CURIE-style).
- Prefixes: `suite:`, `req-class:`, `req:`, `conf-class:`, `conf-test:`, `profile:`, `result:`.
- Cross-part references use `8601-1:` or `8601-2:` prefixes.
- Clause references use RFC 5141 URNs: `urn:iso:std:iso:8601:-{part}:ed-1:en:clause:N`.
- Test IDs follow `conf-test:{prefix}-{type}-{NNN}` (e.g. `conf-test:cal-date-parse-001`). See [the identifier scheme](/docs/identifier-scheme).

### YAML schema

- Every YAML file declares its schema in a header comment: `# yaml-language-server: $schema=...`.
- Run `ruby scripts/validate` after *any* change to YAML.
- Component vocabulary is data-driven from `schema/components.yaml` — don't hardcode component names in code or tests.

### Ruby code (lib/ and adapters/)

- Use `autoload` for internal library code. Define autoloads in the immediate parent namespace's file. Never use `require_relative` for code inside `lib/`.
- Use `LoadResult` value objects from `YamlStore` — don't probe hashes for success/failure.
- String keys in adapter return hashes (`{ "valid" => true }`), not symbol keys.
- No doubles in specs (use real model instances or `Struct`).
- No `send` to private methods, no `instance_variable_get`/`set`, no `respond_to?` for type checks.

### Dashboard (site/)

- Vue 3 with `defineAsyncComponent` for lazy-loaded views.
- Tailwind CSS v4 with inverted gray-scale CSS variables for light/dark mode.
- Don't introduce new font sizes outside the existing scale (see the font table in any recently updated view).
- Composables live in `site/src/composables/`. Reuse `useFormat`, `useStats`, `useStatus` rather than duplicating logic.

## Testing your changes

Run in this order; each catches a different class of problem.

1. **Validate YAML**:

   ```bash
   ruby scripts/validate
   ```

   Catches schema violations, broken cross-references, malformed test definitions, ID naming issues.

2. **Run RSpec**:

   ```bash
   bundle exec rspec
   ```

   Catches module-level regressions in `lib/test_suite/`.

3. **Run conformance tests against an adapter**:

   ```bash
   ruby scripts/run-tests --adapter ruby-date
   ruby scripts/run-tests --adapter "exec:node adapters/node-datetime.js"
   ```

   Catches adapter regressions. Compare the output YAML to the previous run to spot drift.

4. **Regenerate dashboard data**:

   ```bash
   ruby scripts/capability-matrix
   ```

   Regenerates `site/public/summary.json` and `site/public/detail.json`. Spot-check that nothing went sideways.

5. **Build the dashboard**:

   ```bash
   cd site && npm run build
   ```

   Catches Vue compile errors and Tailwind issues. Run `npm run preview` to view locally before opening a PR.

## Opening a pull request

1. Create a feature branch off `main` (do not commit to `main` directly).
2. Make focused commits — one logical change per commit.
3. Include updated YAML results (`results/*.yaml`) if you changed anything in `requirements/`, `tests/`, `profiles/`, or any adapter.
4. Include regenerated `summary.json` and `detail.json` if you changed adapters, requirements, tests, or `capability_matrix.rb`.
5. Reference any related issue in the PR description.
6. CI runs `ruby scripts/validate`, `bundle exec rspec`, and the dashboard build. All three must pass.
